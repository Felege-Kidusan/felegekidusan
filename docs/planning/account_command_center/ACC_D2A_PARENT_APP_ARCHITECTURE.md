# D2-A — Parent App ↔ Account Command Center: Architecture

**Status:** DRAFT v0.1 · **Date:** 2026-10-18 · Part of D2 (see `ACC_D2_ARCHITECTURE.md` for the shared foundation).
**Governing specs:** `PARENT_APP_FEATURE_BASELINE.md` (locked; §1 account/activation, §13 settings, §15 offline/Amharic, §16 privacy), D1 v1.1 (§6 states, §7 credentials, **§7a identifiers**).
**Product identity:** OAuth client `fkss-parent-app` · API namespace `/api/parent/v1` · account kind `parent` · consent set `parent-v1`.

---

## 1. What is specific to the Parent app

| Aspect | Parent-specific rule |
|---|---|
| Who the account is | The **guardian** (`guardians.id`), never the child (D1 ID-3) |
| What the parent types | A **child's member ID** at activation / new-device only (ID-1, ID-7) |
| What the parent sees | Exactly the children linked to that guardian in `member_guardians`, with per-child link status (ID-5) |
| Two guardians, one child | Each has their own account; the desk code selects the guardian (ID-4) |
| Legal/custody removal | School-admin T2 flips the per-child link status to `removed_by_sa`; the account itself stays (ID-6) |
| Privacy | No e-mail/phone required; optional notification channels only inside a trusted session (baseline §16) |
| Language | Amharic-first UI; English fallback; all ACC messages delivered as message *codes* that the app localises |

## 2. Flows

### 2.1 First activation (at the office — D2-3 recommendation: code consumed at the desk)
```
Desk (Command Center)                                  Parent phone (app)                         ACC Core
1 accounts_office verifies parent identity + children
2 confirms each child link exists in Family Link
  (if not → HR T2 card; stop)
3 records proofing (evidence, children, consent, legal-check)
4 "Issue activation code" → code shown once (+QR)
                                                       5 Install app → "Activate" → scan QR / type
                                                         child ID + code
                                                       6 App generates P-256 key in keystore,
                                                         biometric-gated; sends {child_id, code,
                                                         pubkey, device_info}            ─────────▶  7 resolve child → guardian candidates;
                                                                                                        code must match ONE of them; code single-use
                                                                                                     8 create device (ENROLLING→ACTIVE)
                                                       9 Set 6-digit PIN (twice)       ─────────▶  10 PIN stored peppered+hashed; account → ACTIVE
                                                                                                     11 issue access+refresh (device-bound)
                                                       12 Home screen shows all linked children      12 events: account.activated, device.registered,
                                                                                                        account.code.used, consent.granted
13 Desk screen shows "Activated ✔ on <device name>" (poll) — slip is destroyed
```
If D2-3 is decided "at home within 72 h", steps 5–12 happen later; the desk shows `PENDING_ACTIVATION` until the code is used, and the parent is told to expect "code used" to appear in their SMS-free world as an in-app notice only.

### 2.2 Daily login
Biometric/device-credential unlocks the keystore key → app signs a device proof → `POST /token` with refresh token (+ proof) → new access+refresh. No ID, no PIN. If `authorization_version` changed (lock, suspend, device revoked) → 401 with code → app shows the reason and returns to "visit the office" or re-PIN as applicable.

### 2.3 PIN step-up
Required: first use after install; after absolute refresh expiry (180 d); after STALE (60 d unused); after a staff reset; before sensitive screens if the baseline/product decides (e.g., report-card photo, feedback) — **PROPOSED:** PIN before §5 reports and §6 feedback; biometric suffices elsewhere.

### 2.4 Add a second phone
- Self-service from an ACTIVE device: Settings → Devices → "Add device" → shows a short-lived pairing code/QR generated by ACC (24 h, single use, bound to the account) → new phone scans → enrols its own key → PIN entry on the new phone (must know the PIN) → both devices listed. Max 3 (D1).
- At the desk: `accounts_office` issues an add-device code (T0) after proofing-lite (identity only).

### 2.5 Phone lost / stolen / broken
- From another own device: Settings → Devices → revoke the lost one (self-service, logged as `device.revoked` by user).
- Else at the desk: identity check → `accounts_office` revokes the device (T0) → sessions die immediately → new phone enrolled with an add-device code. Nothing requires approval (D1: protective actions are never gated).

### 2.6 Forgotten PIN
Desk only: proofing → reset code (24 h) → all sessions revoked → parent enters code on the phone, sets a new PIN; existing devices stay enrolled unless the parent asks otherwise. In-app notice on all devices: "Your PIN was reset at the office on …".

### 2.7 Account closure (baseline §13)
From the app: request closure → account `SUSPENDED (user_request)` immediately, T0 closure by desk within the policy window after an in-app confirmation; data minimised after 12 months (D1 §9). From the desk: user-requested T0; not requested T1.

## 3. API surface (namespace `/api/parent/v1`) — contract detail in D3

| Group | Endpoints (shape) | Auth |
|---|---|---|
| Activation | `POST /activation/resolve` (child ID + code → guardian display name masked, consent text version) · `POST /activation/complete` (pubkey, device info, PIN) | code + rate limit |
| Token | `POST /token` (grant `device-assertion` or `refresh_token`) · `POST /revoke` | device proof |
| Session/self | `GET /me` (account, children + link status, devices, consent state) · `POST /me/pin` (change PIN) · `GET /me/devices` · `POST /me/devices/{id}/revoke` · `POST /me/devices/pairing-code` · `POST /me/closure-request` · `GET /me/notices` | access token (device-bound) |
| Child data | `GET /children/{id}/today`, `/attendance`, `/reports`, `/feedback`, `/profile`, … (baseline §3–§12; built in the parent-app programme, not in ACC) | access token + **link check per request** |
| Consent | `GET /consent/current` · `POST /consent/accept` | access token |

**Link check per request (hard rule):** every child-data handler calls `ParentScope::assertLinked(sub, child_id)` which joins `acc_accounts → guardians → member_guardians` *live* and respects `removed_by_sa`; no cached child lists on the server side. Reads of sensitive data emit `access.sensitive.read`.

## 4. Scopes
`parent:profile parent:children:read parent:devices parent:consent parent:notices` (+ later `parent:messages`, `parent:feedback:write`). Scopes are per client; the Parent app can never obtain `member:*` scopes and vice versa.

---

## 5. Offline & degraded behaviour (baseline §15)
- Access token ≤ 15 min; cached data shown with "last updated" stamp; writes queue with idempotency keys (pattern FACT in staff app).
- If `authorization_version` mismatch is returned, cache is wiped for child data (safety on revoked device) — **PROPOSED**.
- Activation/reset/add-device are online-only by design.

## 6. Events emitted by the Parent app paths (subset of shared vocabulary)
`account.code.used`, `account.activated`, `authn.unlock.success/fail`, `authn.pin.fail/fail_max`, `authn.token.refreshed/revoked`, `device.registered/renamed/revoked(by=user)`, `device.pairing_code.issued/used`, `consent.granted/withdrawn`, `account.closure.requested`, `access.sensitive.read{child_id,kind}`, `link.denied_request` (parent tried a child not linked).
